## Git Convention

### 브랜치
- `main`: 배포용 브랜치
- `dev`: 개발 통합 브랜치
- 작업 브랜치는 최신 `dev`에서 생성합니다.
- 이름: `타입/이슈번호-작업명`
  - `feat/1-common-response`
  - `chore/3-swagger`

### 커밋 메시지
형식: `타입: 작업 내용 (#이슈번호)`

| 타입 | 용도 |
| --- | --- |
| feat | 기능 추가 |
| fix | 오류 수정 |
| refactor | 기능 변경 없는 코드 개선 |
| docs | 문서 수정 |
| test | 테스트 추가·수정 |
| chore | 설정·의존성 등 기타 작업 |

예시:
- `feat: 공통 응답 및 예외 처리 구현 (#1)`
- `chore: Swagger 설정 추가 (#3)`
- `fix: 운영 환경 Swagger 비활성화 (#3)`

### 작업 순서
1. 이슈 생성
2. 최신 `dev`에서 작업 브랜치 생성
3. 구현 및 테스트 후 커밋·push
4. 작업 브랜치 → `dev`로 PR 생성
5. 변경 사항과 테스트 결과를 작성하고 리뷰 후 머지

### PR
- 제목은 커밋 메시지와 같은 형식을 사용합니다.
- PR 템플릿에 변경 사항·관련 이슈·테스트 결과를 작성합니다.
- API가 변경되면 Swagger 문서도 함께 수정합니다.
- 비밀번호·API 키·환경변수 파일은 커밋하지 않습니다.

- ### 이슈 제목
형식: `[타입] 작업 내용`

- `[Feat] 공통 응답 및 전역 예외 처리 구현`
- `[Chore] Swagger API 문서 설정`
- `[Fix] 주차장 조회 오류 수정`

### PR 제목
형식: `타입: 작업 내용 (#이슈번호)`

- `feat: 공통 응답 및 전역 예외 처리 구현 (#1)`
- `chore: Swagger API 문서 설정 (#3)`
- `fix: 주차장 조회 오류 수정 (#5)`

※ 괄호 안 번호는 PR 번호가 아닌 관련 이슈 번호입니다.
